## 1. サービスの定義と未来の背景

[目次へ戻る](#contents)

ミライフは、年齢に関係なく、利用者が知識や経験を教え、他者の教材から学び、プロフィールと受講履歴に基づくAI未来ナビで次の学びや挑戦に気づく、PC向けの3D交流・学習サービスである。「何歳からでも、新しい未来へ挑戦できる人生アップデート空間」を掲げる。誰でも分野によって教える側・学ぶ側になれる。

100年後の社会設定を企画の必須説明に含める。チームメイト案の2127年は具体年の候補であり、予測事実ではない。長い人生で仕事・趣味・役割を繰り返し変え、技術の変化に応じて学び直す一方、自分の経験の価値や次に学びたいことに気づく機会が不足する、という未来像を想定する。ミライフは知識を循環させ、本人が新しい可能性を発見できる場を目指す。具体年の採否はQ-01で確認する。

機能分類は改善案を受け「学ぶ・教える・つながる・未来ナビ」の4つに整理する。学ぶに趣味・生活知識・仕事のスキルを含め、挑戦は教材から学んだことを実際に試し、次の学びへ進む意味であり、この理解は利用者が確認済み。料理や仕事等を3D内で再現して操作するシミュレーションは対象外。実践の自動検出・技能判定は要求していない。分類数は3Dの建物数や通話室数を意味しない。

基本の流れ：登録・ログイン→プロフィール登録→教材を投稿する／教材を学ぶ→本人が受講完了を記録→AIがプロフィールと履歴からミライフ内の次の教材を提案→利用者が選んで学ぶ。交流はこの流れのどの段階からも利用できる。

## 2. 優先度と決定の確度

[目次へ戻る](#contents)

| 優先度 | 現在の範囲 |
|---|---|
| [Must](#priority-must) | 予約制オンライン講座（内容・日時設定、日程一覧、予約・取消・定員管理・開催）、一般向け自由登録・ログイン（未成年の利用条件は再検討中）、プロフィール（教えられること／学びたいこと／実年齢の表示／資格登録）、利用者の教材・動画投稿、動画の直接ファイルアップロード、教材閲覧、本人操作の受講完了と履歴保存、実AI未来ナビ、PCのUnity 3D、共有移動・4室の通話 |
| [Should](#priority-should) | アバターの外見選択、経験談の投稿・閲覧、通報・運営による教材公開停止（時間があれば実装）。委任された追加案として「あとで学びたい」保存 |
| [Could](#priority-could) | 教える人と教わる人のマッチング |
| [Future](#priority-future) | 講座以外の活動・イベント予約、スマートフォン・タブレット・スマートウォッチ等の端末対応、先生の特徴を学ぶPRY |
| [Candidate](#priority-candidate) | 採否未決の補完機能。認証復旧等は方式と運用範囲を決める。通報・教材停止はShouldへ確定 |
| [対象外](#priority-out-of-scope) | 3D内の料理・職業等の体験シミュレーション、VR/HMD、録音録画、画面共有、近接通話、文字チャットの新規追加。別の合意なしに採用しない |

「確定」＝利用者の明示回答で決まった機能・方針。「継承」＝原資料にあり変更されていない制約。「導出」＝確定機能を成立させるための要件。「提案」＝入力上限・時間・設計方法等の未承認案。「未決」＝Q一覧で選択を要する事項。Mustという優先度だけで提案数値や技術方式まで承認されたとは扱わない。

完成版はログイン必須・永続履歴・Unity 3D・実AIである。旧ゲスト2D版は過去の実装報告であり、現在の完成要件へ混ぜない。Shouldの省略理由を記録し、Could／FutureをMustの前提にしない。

## 3. 主体・権限

[目次へ戻る](#contents)

| 主体 | 操作の範囲 |
|---|---|
| 未ログイン | 紹介・認証入口。個人データ・広場・教材利用は認証後 |
| 利用者 | 自分のプロフィール・投稿・履歴を管理し、公開教材を学ぶ |
| 投稿者 | 専用の固定身分ではなく、自分の教材に対する所有者権限 |
| 運営 | 採用する場合のみ、定義した公開停止等の権限を持つ。一般利用者に付与しない |

表示名は識別の見た目であり本人確認に使わない。userId（永続アカウント）とparticipantId（その時の広場参加）を分離する。全利用者に教える可能性があり、年齢・性別で役割を固定しない。年齢を「54歳」のように実年齢でプロフィールから閲覧できる。資格登録を追加する。年齢入力の必須性・閲覧相手・更新方式・AI利用ON／OFFは詳細設計事項。一般利用者が自由に登録できるサービスを想定する。

## 7. 操作単位の機能要件

[目次へ戻る](#contents)

各操作を同じ項目で記載する。認証方式等が未決なら関連部分の実装を確定せず、Qを解決する。Must以外の試験は採用したときの条件であり、全試験を無条件に完成ゲートへ加えない。

<a id="fr-001"></a>

### FR-001 サービス内容を確認しログイン入口へ進む

- **優先度**：Must
- **根拠**：§1〜4、6.1、12.2。原資料継承＋最新会話。操作詳細・提案値はレビュー対象
- **画面**：SCR-01
- **操作主体**：来訪者
- **前提条件**：トップページにアクセスできる。
- **入力・制約**：「広場へ参加」操作。ログインや機器の許可は要求しない。
- **正常処理**：サービス名、未来の社会設定、学ぶ・教える・つながる・未来ナビの4分類を表示する。利用開始を選ぶとログインへ進み、認証済みならホームへ進む。教材やAIに試験用データを使う場合は識別する。
- **異常・例外**：未実装のリンクは押せるように見せず「準備中」と表示する。取得障害時は再試行の案内を表示する。
- **事後条件**：公開紹介を閲覧できる。広場・個人データの利用は認証後とし、紹介閲覧だけでは広場の枠を消費しない。
- **未決事項**：—

- **AC-001-01**：未ログイン状態で、紹介から利用開始を選ぶと、ログインへ進む。個人の履歴を返さず、広場枠と機器許可を要求しない。
- **AC-001-02**：ログイン済み状態で、利用開始を選ぶと、本人のホームへ進み、他者の履歴は表示しない。

<a id="fr-002"></a>

### FR-002 表示名を登録・変更する

- **優先度**：Must
- **根拠**：§12.1（文字条件は追加案）。原資料継承＋最新会話。操作詳細・提案値はレビュー対象
- **画面**：SCR-10
- **操作主体**：ログイン利用者
- **前提条件**：本人のプロフィール編集画面を表示している。
- **入力・制約**：P-01：前後空白除去後1〜20文字。文字数は利用者に見える文字単位。内部空白・日本語・絵文字を許可し、改行・制御文字・空白のみは拒否する。同名は許可する。
- **正常処理**：P-01案の規則で入力を検証して保存する。同名を許可し、本人識別はuserIdで行う。変更を共有中の表示へどう反映するかは現在の参加中も反映する案。HTMLとして解釈しない。
- **異常・例外**：未入力・空白のみ・上限超過・禁止文字は理由を表示し保存しない。既存名は保持する。
- **事後条件**：次回ログイン後も表示名を保持する。プロフィール変更で広場枠は増減しない。
- **未決事項**：Q-02、Q-06

- **AC-002-01**：本人のプロフィール状態で、空白のみ・1文字・20文字・21文字を保存すると、P-01案に従い空白と21文字は拒否、1と20文字は有効。別アカウントと同名でも本人IDは別。
- **AC-002-02**：記号やHTMLを含む表示名状態で、保存して表示すると、テキストとして表示しスクリプトを実行しない。
- **AC-002-03**：表示名を保存済み状態で、ログアウト後に再ログインすると、本人の保存した名前が表示される。

<a id="fr-003"></a>

### FR-003 アバターの外見を選ぶ（Should）

- **優先度**：Should
- **根拠**：原資料§6.3・12.1。2026-10-07の利用者指示で選択機能をShouldへ変更（DEC-013）。原資料継承＋最新会話。操作詳細・提案値はレビュー対象
- **画面**：SCR-02
- **操作主体**：ログイン利用者
- **前提条件**：ログイン済み。入場画面に選択機能がある場合に利用する。未実装時は標準アバターを利用する。
- **入力・制約**：アバターを選ぶ場合は許可IDを1つ指定する。省略可。外見のアップロードは完成版の対象外。
- **正常処理**：選択機能を提供する場合は候補と選択状態を表示し、入場前に変更できる。年齢や性別によって候補を制限しない。
- **異常・例外**：選択取得に失敗した場合は標準アバターで参加する導線を示す。不正IDの入場拒否はMustのFR-005で定義する。
- **事後条件**：選択した場合は自分と他者に同じ外見が表示される。未選択・機能未実装は入場失敗の理由にしない。
- **未決事項**：Q-02

- **AC-003-01**：選択機能があり、有効な名前と候補一覧を表示中状態で、候補を選んで参加すると、選択したアバターが自分と他端末で一致する。
- **AC-003-02**：選択機能で候補Aを選択済み状態で、入場前に候補Bへ変更して参加すると、最後に選んだBが反映され、Aの古い選択が上書きしない。

<a id="fr-004"></a>

### FR-004 入場前に機器を任意で確認する

- **優先度**：Must
- **根拠**：§12.1（停止条件は追加案）。原資料継承＋最新会話。操作詳細・提案値はレビュー対象
- **画面**：SCR-02
- **操作主体**：ログイン利用者
- **前提条件**：ログイン後の広場入場画面を表示し、機器確認は任意。
- **入力・制約**：「カメラ確認」「マイク確認」を個別に選ぶ。スキップ可能。
- **正常処理**：選んだ機器だけの許可を要求する。カメラはローカルプレビュー、マイクは入力レベルを示す。入場前の音声・映像は他参加者へ送らない。終了・入場・画面離脱で確認用トラックを停止する。
- **異常・例外**：機器なし・拒否・使用中・安全な接続でない場合は日本語で理由と参加可能なことを示す。再試行は明示操作で行う。
- **事後条件**：確認結果に関係なく機器なしで参加できる。確認を終えると取得を停止し、広場の送信設定は両方OFFになる。
- **未決事項**：Q-04

- **AC-004-01**：機器許可をまだ与えていない状態で、確認をせず参加すると、機器許可なしでロビーに参加し、送信は両方OFF。
- **AC-004-02**：確認用にカメラ・マイクを開いている状態で、確認終了または入場すると、確認用取得を停止し、他参加者に音声・映像を送らない。
- **AC-004-03**：権限拒否または機器なし状態で、確認を試すと、理由とスキップ案内を表示し、参加を妨げない。

### FR-005 ログインした本人として3Dロビーへ入場する

- **優先度**：Must
- **根拠**：§12.1、12.4（重複防止は追加案）。原資料継承＋最新会話。操作詳細・提案値はレビュー対象
- **画面**：SCR-02→03
- **操作主体**：ログイン利用者
- **前提条件**：サーバーで認証が有効。表示名が保存済み。共有サーバーへ接続可能で、FR-201の3D準備が完了している。
- **入力・制約**：認証された接続、requestId、任意avatarId。userIdはサーバーが認証情報から得る。avatarId省略時は標準IDを割当。明示的な不正IDは拒否する。
- **正常処理**：認証と入力を検証し、定員確認・本人の参加枠作成・要求結果の記録を原子的に行う。同一要求は同じ結果を返す。1アカウント1有効参加を基本案とし、別タブで重複入場させない。
- **異常・例外**：未認証・認証失効はログインを案内。満員・不正IDは理由を表示。応答不明なら同一requestIdで結果確認する。認証成功だけで広場枠を消費しない。
- **事後条件**：userIdに結び付いたparticipantIdが1つ存在し、ロビーに所属する。機器送信はOFF。
- **未決事項**：Q-02、Q-03、Q-06、Q-15

- **AC-005-01**：認証済み、全体49枠状態で、入場すると、本人の枠が1つ増え全体50枠。userIdはクライアントの任意指定で置換できない。
- **AC-005-02**：入場要求中状態で、同じ要求を再送し別タブでも入場すると、同じ要求で重複作成しない。1アカウント1参加案に従い別タブの新規入場を拒否する。
- **AC-005-03**：認証済み、アバター未選択状態で、入場すると、標準モデルを自分・他PCに表示し、選択UIなしでも移動・通話できる。
- **AC-005-04**：未認証または不正avatarId状態で、入場要求すると、枠を作らず理由を返す。

- **前提条件**：ログイン・利用権限が有効。対象操作の所有権と開催状態をサーバーが検証する。
- **入力・制約**：講座ID、開始日時、終了日時、受講者定員。部屋割当はQ-22方式。

- **異常・例外**：締切を過ぎた新規募集・締切の任意上書き・定員超過・会場競合を拒否。予約者がいる日程を黙って変更しない。

- **根拠**：予約制のオンライン講座を成立させるための導出要件。方式・数値の未合意部分は提案またはQとして区別する。

### FR-321 予約した開催回の会場へ入り講座を開始・終了する

- **優先度**：Must
- **根拠**：予約制のオンライン講座を成立させるための導出要件。方式・数値の未合意部分は提案またはQとして区別する。

- **AC-321-02**：講師と受講者状態で、開始・終了操作を要求すると、講師だけが開催状態を変更でき、終了後も本人完了は別操作。

### FR-322 講師が開催を中止し予約者へ知らせる

- **優先度**：Must
- **根拠**：予約制のオンライン講座を成立させるための導出要件。方式・数値の未合意部分は提案またはQとして区別する。
- **画面**：SCR-19、18
- **操作主体**：講師（自分の開催回の所有者）
- **前提条件**：ログイン・利用権限が有効。対象操作の所有権と開催状態をサーバーが検証する。
- **入力・制約**：開催回ID、中止理由、確認操作。日時変更は別案として扱う。
- **正常処理**：講師本人が対象回を中止し新規予約を停止する。予約に中止状態を反映し、予約者の予定に知らせる。最低限の通知はアプリ内の予定・通知表示案。メール等の追加通知方式は未決。

- **AC-322-02**：中止処理と予約が競合状態で、同時に操作すると、中止後の有効予約を残さず、利用者に最終状態を示す。

### FR-324 プロフィールの資格を登録・編集・削除する

- **優先度**：Must
- **根拠**：利用者の今回指示：プロフィールに資格等を登録可能にする。項目詳細・公開範囲・確認方式は設計案。
- **画面**：SCR-10
- **操作主体**：ログイン利用者
- **前提条件**：本人がプロフィール編集画面を開いている。
- **入力・制約**：資格名を基本項目とし、発行団体・取得年月・級等を任意項目とする案。複数件登録可。文字数・件数上限はQ-23。証明書画像や資格番号は今回の登録機能に必須化しない。
- **正常処理**：本人が資格を追加・編集・削除して保存できる。プロフィールの資格一覧に表示する案。初期は自己申告として扱い、証明書提出・運営審査・認定バッジは追加採用まで実装しない。登録しただけで資格保有をシステムが確認したと表示しない。
- **異常・例外**：資格名が空・不正入力・他者の資格変更・古い版での更新は拒否し入力を保持する。二重送信で同じ登録を増やさない。
- **事後条件**：次回ログイン後も本人の登録を保持し、閲覧権限のある利用者が登録内容を見られる。資格なしでも学習・投稿・開催を妨げない案。AI利用や資格による検索・講師の認定は別途採否を決める。
- **未決事項**：Q-19、Q-23

- **AC-324-01**：資格名と任意項目を入力した本人状態で、追加して再ログインし公開プロフィールを確認すると、登録が保持され、許可範囲へ表示。自己申告を運営確認済みとして表示しない。
- **AC-324-02**：本人の資格がある状態で、内容を更新して削除すると、本人の登録だけが変更・削除され、公開表示にも反映する。
- **AC-324-03**：資格なし／資格名空欄状態で、通常利用／空の資格追加を行うと、資格なしでも利用可。名前のない資格レコードは作らない。
- **AC-324-04**：別利用者の資格IDまたは同じ追加要求状態で、更新・削除または追加再送すると、他者変更は拒否し、同じ要求による二重追加を防ぐ。

## 14. 予約制オンライン講座と固定締切

[目次へ戻る](#contents)

「学ぶ」と「教える」は同じ講座・開催回の受講者側と講師側の入口。講師が内容と日程を登録し、受講者が予約して当日集まる。動画・資料は引き続き予約不要で、講師不在でも閲覧できる。

確定した締切：bookingClosesAt = startsAt − 30分。新規予約はサーバーで処理を確定する時点のnow < bookingClosesAtでのみ受理する。境界時刻ちょうどは不可。開始30分前は講師が変更できない共通ルールであり提案値ではない。受付停止のバッチが遅れても保護APIは直接時刻を確認する。公開時にすでに締切を迎えた回は新規募集しない。

設計案：日時をUTCで保持し、利用画面にはタイムゾーン付きで表示する。国内向け初期表示は日本時間。締切判定を端末時計に任せない。開始日時と締切の整合はサーバーで維持する。

未決：予約取消の期限、遅刻・途中入室・入室開始時刻、講師不在、最少人数、予約0人時の処理、日程変更の方法。受講者最大7人・最少1人は初期案で、今回の締切合意と同時に承認された値ではない。予約制講座を無料以外へ変更する料金・決済は未採用。

会場の部屋枠と広場50枠の調整はQ-22の実装前決定事項。将来開催回を予約した時点で現在の広場枠を消費する設計にはしない。一方、当日の満員で予約者を排除しないための容量配分は別途必要。現時点で入場保証を実装済みと扱わない。

### 16.1 現在の構成と実装範囲（2026-10-20）

永続データの保存基盤としてPostgreSQL 17とPrisma 7.10.1を導入済み。ローカルではDocker Composeで開発用DBと独立したテスト用DBを起動する。モデルは `prisma/schema.prisma`、スキーマ変更履歴は `prisma/migrations/`、Next.jsサーバー専用の接続処理は `server/db/client.ts` で管理する。

### 16.2 保存するデータ

業務用12テーブルに認証用4テーブルを追加し、全16テーブルをアプリ用の `app` スキーマに配置する。

| モデル／テーブル | 保存内容・役割 |
|---|---|
| User／users | 永続userId、メール、アカウント状態、作成・更新・論理削除日時 |
| AuthIdentity／auth_identities | ユーザーと認証事業者の識別子・subjectの対応。パスワードや認証トークンは保存しない |

| PolicyConsent／policy_consents | 同意した規約等の識別子・版・同意日時 |
| MediaAsset／media_assets | ファイルの所有者、保存キー、動画・資料の種別、処理状態、MIMEタイプ、サイズ |
| LearningMaterial／learning_materials | 教材の投稿者、題名・説明・分類・タグ、公開状態、メディア参照、版、論理削除日時 |
| MaterialProgress／material_progress | 本人の受講状態・完了日時、参照した教材の版と題名スナップショット |

動画・資料のファイル本体はオブジェクトストレージへ置く方針で、DBにはメタ情報と保存キーを保持する。ストレージサービスの選定・アップロード処理は未実装。署名付きURL、平文パスワード、広場の高頻度な位置・音声・映像はDBへ永続保存しない。資格情報のハッシュとセッション識別子は認証専用テーブルで保持し、APIのJSONやlocalStorageへ渡さない。広場の一時的なparticipantIdと永続userIdも分離する。

<a id="section-16-3"></a>

### 16.3 整合性と運用

- メール・外部認証ID・同じ利用者による同一開催回の予約などの重複を制約で防ぐ。アカウントは既定で `PENDING`。現在はメール未確認の開発版ログインと本人用マイページまでを許可し、予約等の通常権限を持つ `ACTIVE` へ自動で昇格させない。
- メディア所有者と教材投稿者を一致させる。教材の論理削除後も受講履歴と当時の題名を保持し、本人の受講完了を自動判定へ置き換えない。
- 予約はDB側の制約・トリガーで同時処理を制御する。定員超過、講師本人・未有効アカウントの新規予約、開始30分前以降の新規予約を拒否し、取消時は席を解放する。広場50枠・通話室の枠調整は別途設計する。
- `DATABASE_URL` はアプリ実行用、`DIRECT_URL` はマイグレーション用の接続として分ける。秘密情報は環境変数で管理し、クライアントやGitへ公開しない。
- 適用済みマイグレーションは書き換えず、後続の変更として管理する。テストは独立したローカルDBで実行する。本番への切り替え前に制限された実行ロール、バックアップ・復元、認証・権限を持つAPIとの接続を確認する。

<a id="section-16-4"></a>

### 16.4 将来的なSupabaseへの移行方針

将来的に、現在のPostgreSQL基盤からSupabaseへの移行を検討している。現時点では移行先の候補であり、採用時期・プラン・リージョンは未確定。Supabase上の環境作成、接続、実データ移行はまだ行っていない。

第一案は、PostgreSQLとPrismaによるモデル・マイグレーションを維持し、DBのホスティング先をSupabaseへ切り替えること。接続先を変更するだけで移行が完了すると扱わず、以下を移行計画で確認する。

- `app` スキーマ、制約・予約トリガー、既存データ・ID・履歴を維持できるか検証する。新規環境へのスキーマ適用と、既存データの移送・照合を分けて行う。
- 実行用・マイグレーション用の接続、接続プール、TLS、権限、バックアップ・復元を検証する。切り替え時の停止時間・切り戻し方法も決める。
- 当面はサーバー側のPrisma接続を基本とし、`app` スキーマをブラウザーから直接操作する公開APIの対象にはしない。直接アクセスを採用する場合は、認証・公開範囲・行単位の権限制御を別途設計・検証する。
- Supabase AuthやStorageの採用は、DBホスティングの移行とは別に検討する。採用時は `User` / `AuthIdentity` との対応、本人確認・保護者確認、メディア所有権・アクセス制御を設計する。

## 18. Unityへの本人表示の引き継ぎ（2026-10-21）

[目次へ戻る](#contents)

Webで登録した表示名・アバター・教えたいこと・学びたいことを、同一サイトのUnityへ引き継ぐ。利用者の選択により未ログインのゲスト見学を残す。年齢・資格はWebで未収集のため、デモ人物の値を本人情報に使わない。登録アバターはワールド上部のアイコンと人型アバターの服の色に対応する。

サーバーがCookieから本人を識別し、最小プロフィールだけを返す。メール・非公開の目標・資格情報・トークンをUnityへ渡さない。Unityから指定されたuserIdで他者を取得しない。別タブのログイン・ログアウト、表示中の定期確認とフォーカス復帰時の確認で表示を更新する。失効や確認の通信失敗では前の本人情報を消してゲスト表示へ切り替える。

本人の切り替え時は前のUnity内のお試しデータも消す。教材・予約・AI・通話の保存や操作API、プロフィール編集、複数人同期は今回の接続範囲に含まない。これらの完成版要件は維持する。具体的な実装と検証は [Unity共有手順](../unity/README.md) を参照。
